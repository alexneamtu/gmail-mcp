# Gmail MCP Implementation Plan

**Goal:** Build and configure a single-user, remote, multi-account Gmail MCP service.

**Architecture:** Express hosts MCP and oidc-provider. Google provides owner identity and separate mailbox grants. A local administrative CLI manages encrypted state and enrollment.

**Tech Stack:** TypeScript, official MCP v2 SDK, oidc-provider 9, Google auth/Gmail clients, Node SQLite and crypto, systemd, Caddy.

**Spec:** `docs/superpowers/specs/2026-10-08-gmail-mcp-design.md`

## Global constraints

- No sends during testing. Default read+draft, no sends unless configured.
- Every tool requires a configured account alias, including listing.
- State outside repository; 0600 files, 0700 directory; no sensitive logs.
- Human authorship only. No service or firewall changes without the concrete approval required by the user.
- Treat tracked files as future public content. Use synthetic identities and reserved example domains; keep operator settings and private reports outside the repository.

## Review focus

- Concurrent/replayed OAuth code or refresh-token consumption must fail closed.
- Encrypted database indexes and WAL must not reveal bearer values.
- Reauthorization may not replace a mailbox with a different identity.
- Revocation must invalidate current access, not only future refreshes.
- Malformed tool input, mail headers and upstream failures may not leak secrets or trigger duplicate writes.

## Tasks

1. **Protected persistence and configuration** (`src/store.ts`, `config.ts`, tests): resolve the [storage review](../../storage-review.md), test encryption, tamper detection, restart, permissions and consume/revoke; implement using SQLite, AES-GCM and HMAC; run tests/typecheck.
2. **Gmail tools** (`gmail.ts`, `tools.ts`, tests): test red for aliases, scope modes, unknown fields, bounded results and no write retries; implement API wrapper and MCP registration; run suite.
3. **OAuth and HTTP** (`auth.ts`, `app.ts`, tests): test red for metadata/401, hostile origins, owner pin, code/refresh replay, consent, resource and revocation; configure production provider and implement Google login; run real HTTP integration tests with synthetic identities and no Google calls.
4. **Administration and deployment** (`cli.ts`, deployment files, README): implement private initialization, Google enrollment with state/PKCE, remove/revoke/rotate and config checks; prepare systemd/Caddy files and deployment instructions; test CLI against temporary state and validate configs.
5. **Verification and review**: run typecheck, full tests and local Inspector. Obtain an independent code review, fix material findings and rerun affected checks. Record evidence and all live steps still blocked by user input.
6. **Live setup**: give exact Google Console and browser steps with real domain, wait, then apply approved service/ingress changes and verify real Claude account listing/search/drafts. Write final deployed operations instructions.

## Execution record

- The application lives in a standalone repository.
- Initial storage tests and typecheck pass; the storage review identifies remaining defects and integration requirements.
- Account discovery retains a required known alias.
